## 1. 技术栈

| 层 | 技术 | 证据 |
|---|---|---|
| 构建 | Vite 6.4.6 + TypeScript 5.6 | `package.json`、`vite.config.ts` |
| 前端 | 原生 DOM + 模块化 feature，无 React/Vue | `web/boot.ts` 按顺序装配 feature；`web/features/*/index.ts` |

没有数据库 ORM、没有测试框架（用 `node:test`）、没有 lint 配置。语料库因此也不能引入新依赖——校验脚本只用 Node 内置模块。

## 3. DeepSeek 接入点（全部在后端）

| 位置 | 作用 |
|---|---|
| `server.mjs` `loadLocalEnv()` | 从 `account-service/.env` 读 `AI_API_KEY`，**密钥只在服务端** |
| `server.mjs` 第 37–41 行 | `AI_BASE_URL` / `AI_MODEL` / `AI_VISION_MODEL` / 两个超时 |
| `deepseekReply()` | 非流式对话，带 system prompt + 最近历史 |
| `deepseekReplyStream()` | 流式（SSE），前端逐字显示 |
| `deepseekComplete()` | 通用补全，`/api/ai/chat/completions` 用它，情景模块走这条 |
| `POST /api/chat` | 诺的聊天入口：风险判定 → 拼 prompt → 调模型 → 落库 |
| `POST /api/ai/chat/completions` | 通用多轮补全：只做长度裁剪 + 高风险短路，**不注入诺的人格** |

关键设计：

- 浏览器拿不到 API Key，所有模型调用经 `vite` 代理到 `account-service`。
- 前端 `web/kernel/api.ts` 的 `ai.complete(messages, opts)` 就是 `/api/ai/chat/completions` 的包装（`maxTokens` 默认 400，`temperature` 默认 0.8）。
- 高风险词短路发生在服务端（`riskOf()`），即使前端被绕过也拦得住。

## 4. 情景聊天模块现状

### 4.1 数据模型

`web/features/scenario/scenarios.ts` 定义 `Scenario`：分类、子类、标题、一句话、对方角色、背景、目标、三档开场白、三档风格、禁区、复盘关注点。6 条硬编码数据（`work-raise`、`work-blame`、`family-marriage`、`intimacy-cold`、`friend-loan`、`intimacy-breakup`），另有 8 类 × 14 个子类标签。

### 4.2 流程与状态机

`web/features/scenario/index.ts`：`lobby → setup → roleplay → transition → debrief`，可随时 `safety`。历史存 `localStorage` 的 `nuo_scenario_history_v1`，最多 30 条。

### 4.3 提示词（两套，防串味）

| 函数 | 角色 | 要点 |
|---|---|---|
| `standInPrompt()` | 替身 | 用户演对方，AI 用第一人称替用户回应；先接住、再说立场；1–3 句；不跳出、不分析 |
| `debriefPrompt()` | 诺 | 跳出替身，只输出 CLOSEST / TAKEAWAY / NEXT 三行；不评分 |

`standInPrompt` 里已有一段“圆滑公式”：接住 → 说事实 → 低负担请求 → 留退路。这是**提示词级**的策略，和本语料库的 `strategies` 字段同源，但还没有数据化。

### 4.4 没有后端情景接口

情景模块直接调 `ctx.api.ai.complete([...])`，即 `/api/ai/chat/completions`。没有 `/api/scenario/*`，没有服务端会话，没有检索。这是刻意的 MVP 取舍（见 `docs/product/情景聊天-设计方案-v1.md` 第 13 节“已知缺口”）。

| 台词语料 | `语料库/情景应答/*.jsonl`（49 条） | 未接入，人工参考 |

## 6. 新语料库怎么接（分三阶段，当前只做第 0 阶段）

### 阶段 0（本次）：纯数据，零运行时改动

语料库是**只读静态数据**。校验脚本离线跑，不参与构建，不进 bundle，不碰 API。

- 好处：不会影响现有聊天、不会引入新依赖、不会把未审内容送进模型。
- 代价：FAM-001 现在只是一份 JSON，页面上看不到。

### 阶段 1：生成期适配（建议下一步，仍需人工触发）

写一个离线脚本，把 `PRODUCTION_APPROVED/` 里通过审核的语料编译成前端可用的 `scenario-corpus.generated.ts`，再由 `scenarios.ts` 引入。这样：

- 语料仍是数据，提示词仍是代码，职责不变；
- 构建时没有网络请求，也没有运行时读文件（浏览器读不到本地文件）；
- 只有 `approved` 的字段会进 bundle，未审内容天然进不去。

衔接点：`scenarios.ts` 的 `SCENARIOS` 数组。把 `Scenario` 的字段映射到新结构的子集即可（`openings` ← `opening.openings`，`styles` ← `opening.styleNotes`，`avoid` ← `voice.forbidden`，`debriefFocus` ← `usage.promptHints`）。

### 阶段 2：服务端检索（等语料 ≥ 20 条再说）

新增 `/api/scenario/start|chat|debrief`，把检索、提示词拼装、风险判定都放到服务端：

- 语料不必全量下发到浏览器；
- 提示词与语料版本可以一起回滚；
- 密钥与调用逻辑仍然只在 `account-service`。

**本阶段不做**，原因见 `docs/07-RAG与DeepSeek接入建议-v1.md`。

## 8. 三个必须避免的坑

1. **两份真相。** 语料改了、`scenarios.ts` 没改，页面和文档就会打架。解决：阶段 1 之后，`scenarios.ts` 只做类型与默认值，内容一律来自编译产物。
2. **把研究资料混进正式库。** 已在结构上隔离：`REFERENCE_LIBRARY` 三个桶 + `PRODUCTION_APPROVED` 只收 `approved`，校验脚本会拦住 `research_only` 的引用。
3. **把情景语料写成台词库。** 台词库（`语料库/情景应答`）已经有 49 条，情景库如果也只是句子集合，就白建了。情景库的重点是 `persona / branches / emotionalState / conflict / safety` 这些台词库没有的字段。

## 9. 一句话

> 现有项目缺的不是“更多句子”，是“**一个情景作为一个完整对象**”的数据结构；这次补的就是这个对象，以及围绕它的来源、许可、审核与校验。
