# 数据结构说明 v1

Schema：`schemas/scenario.schema.json`
示例：`ORIGINAL_CORPUS/FAM/FAM-001-父母催婚-v1.json`
模板：`templates/scenario-template-v1.json`

---

## 1. 为什么是这个形状

一句话：**一个情景 = 一个对象，不是一个文件、也不是一串台词。**

设计上刻意做了三个选择：

1. **嵌套分块，不用大平铺。** `counterpart` / `persona` / `voice` / `opening` / `dialogue` 各自成块，前端、提示词、审核各自只读自己那块，不互相污染。
2. **所有文本都可空集合，但关键块不可缺。** 没有 `safety` 的语料不允许存在；没有第二个 `strategy` 的语料会被校验拦下。
3. **状态放两处且必须相等。** 顶层 `status` 方便文件级筛选，`review.status` 保留审核上下文；校验脚本强制两者一致，避免“文件说通过了、审核记录说没有”。

## 2. 十三项能力对照

| 需求 | 字段 |
|---|---|
| 1. 情景基础信息 | `id` `version` `status` `category` `basic` |
| 2. 人物身份与关系 | `counterpart` |
| 3. 性格与行为动机 | `persona` |
| 4. 语言风格 | `voice` |
| 5. 初始情景 | `opening` |
| 6. 多轮对话 | `dialogue.turns` |
| 7. 对话分支 | `branches` |
| 8. 情绪状态 | `emotionalState` |
| 9. 冲突强度 | `conflict` |
| 10. 辅助回应策略 | `strategies` |
| 11. 安全退出条件 | `safety` |
| 12. 来源与许可证 | `sources` |
| 13. 审核状态 | `review` |

另有 `usage`（用途与检索键）和 `schemaVersion`（结构版本）。

---

## 3. 逐块说明

### 3.1 `id` / `version` / `status`

- `id`：`^[A-Z]{3,4}-\d{3}$`，即 `FAM-001`、`SELF-001`。类目前缀（3–4 个字母）+ 三位序号，**永不复用**。
- `version`：语义化版本。改台词 → `1.0.1`；加分支/换策略 → `1.1.0`；改结构或重新定位 → `2.0.0`（同时换文件名的 `-v2`）。
- `status`：`draft` / `in_review` / `approved` / `deprecated` / `rejected` / `blocked`，必须等于 `review.status`。

### 3.2 `category`

`code`（FAM/WRK/REL/FRD/SELF/CNS/CARE/DIG）、`name`、`subcategory`（如“催婚”）、`priority`（P0/P1/P2）。

`code` 必须与所在目录、文件名、`INDEX.json` 三处一致，校验脚本会查。

### 3.3 `basic`

`title`（≤30 字）、`oneLine`（一句目标，8–60 字）、`context`（2–4 句具体背景）、`difficultyDefault`、`difficulties`、`durationMinutes`、`tags`、`locale`。

`context` 的要求是“只写事实，不写心理分析”。写成“她长期控制你，让你很窒息”就废了——那是结论，不是场景。

### 3.4 `counterpart`（人物与关系）

`role`、`relation`、`ageBand`、`powerDistance`、`setting`、`userRole`。

`powerDistance` 是这一块的核心：谁掌握资源、谁能摔门、谁明天还得求谁。没有权力差，冲突就是平的，演练也就没有难度。

### 3.5 `persona`（性格与动机）

`traits`、`surfaceWant`、`underlyingNeed`、`fears`、`triggers`、`coolDowns`。

`surfaceWant` 与 `underlyingNeed` 必须分开：嘴上说“你什么时候结婚”，真正怕的是“你以后一个人没人管，我在亲戚面前也抬不起头”。这两层决定了替身该接哪一句。

`triggers` / `coolDowns` 是检索和分支的钩子，不是给用户看的。

### 3.6 `voice`（语言风格）

`register`、`sentenceStyle`、`verbalTics`、`forbidden`、`sampleLines`。

`forbidden` 是硬边界，必须与 `safety.hardStop` 呼应。`sampleLines` 是“这个人可能说的话”，不是标准答案，也不要求进入对话正文。

### 3.7 `opening`（初始情景）

`scene`、`stakes`、`userGoalDefault`、`openings`（三档开场白）、`styleNotes`（三档对方行为）。

三档不是“语气强弱”，是**行为差异**：温和只转移一次话题；真实会打断、给模糊承诺；难缠会施压、否定、转移责任，但不辱骂、不威胁。

### 3.8 `dialogue`（多轮）

`format` + `turns[]`，每轮：`turn`、`speaker`（`counterpart` / `user_stand_in`）、`text`、`emotion`、`intensity`（1–5）、可选 `strategy`（指向 `S*`）。

约定：`counterpart` 先开口；替身台词 ≤ 3 句；回合数 4–24（示例是 10 轮）。`user_stand_in` 是**示例版本**，不是唯一答案——提示词里必须写“只学结构，不照抄”。

### 3.9 `branches`（分支）

`id`（B1…）、`afterTurn`、`trigger`、`condition`、`leadsTo`（`continue` / `escalate` / `deescalate` / `exit`）、`hint`。

`afterTurn` 不得超过对话最大轮次。至少一条分支的 `leadsTo` 不能是 `continue`，否则就是假分支。

### 3.10 `emotionalState`（情绪）

`scale: "1-5"`、`start`、`arc[]`、`end`、`deescalation`。每个点：`label`、`valence`（-5…5）、`arousal`（1–5）、可选 `atTurn`。

情绪是给生成模型和复盘用的“温度曲线”，不是给用户看的分数。`deescalation` 要写成可执行的动作（先接哪句、再落到什么），不是“安抚情绪”。

### 3.11 `conflict`（冲突强度）

`scale`、`initial`、`peak`（都 1–5）、`escalators`、`deescalators`、`hardLimit`。

`peak` 是这一情景允许达到的上限。`hardLimit` 是写死的天花板：辱骂、威胁、暴力、断绝关系，一律不进。

### 3.12 `strategies`（辅助回应策略）

`id`（S1…）、`name`、`when`、`example`、`avoid`、`intensity`（`soft` / `medium` / `firm`）。

至少 2 条。`avoid` 是必须项：只说“该怎么接”会退化成话术库，写清“哪种接法是错的”才有训练价值。

### 3.13 `safety`（安全退出）

`exitConditions`、`stopSignals`、`hardStop`、`route`、`exitLine`、`afterExit`。

- `exitConditions` ≥ 2，且必须是用户能直接触发的（说“停”、出现某类表述）。
- `hardStop` 覆盖正在发生的危险。
- `route`：`high_risk_protocol`（默认）/ `professional_referral` / `no_roleplay`。
- `afterExit` 写清退出后去哪：热线 12356、110 / 120、转介。只写“退出”不算完。

### 3.14 `sources`（来源与许可）

`origin`（`original` / `adapted` / `licensed`）、`sourceIds[]`、`license`、`licenseClass`、`attribution`、`collectedAt`、`notes`。

硬规则：`licenseClass != commercial_ok` 的语料**不能** `approved`。`sourceIds` 必须能在 `REFERENCE_LIBRARY` 三个桶里查到。

### 3.15 `review`（审核）

`status`、`checklist`（`safety` / `license` / `language` / `realism` / `bias`，各 `pass` / `fail` / `pending`）、`reviewers[]`（`name` / `role` / `at`）、`nextReviewAt`、`notes[]`。

进正式库要求：五项全 `pass`，且至少一位审核人 `role != author`。

### 3.16 `usage`（用途）

`surfaces`（`scenario_chat` / `ai_chat` / `report` / `training_only`）、`promptHints`、`retrieval.keys`、`retrieval.embedding`。

`promptHints` 是给生成模型的分寸提示，**不写具体台词**，否则又变成硬编码提示词。

## 4. 不变量（校验脚本会查）

1. `id` 前缀 = 目录代码 = `INDEX.json` 的类目。
2. 文件名以 `id` 开头；`approved` 文件只能出现在 `PRODUCTION_APPROVED/`。
3. 顶层 `status` == `review.status`。
4. `approved` ⇒ 五项 `pass` 且有非作者审核人。
5. `approved` ⇒ `licenseClass == commercial_ok`。
6. `sourceIds` 必须全部可解析。
7. `turn.speaker` 交替出现，从 `counterpart` 开始；`turn` 连续递增。
8. `branches[].afterTurn` ≤ 最大 turn；`strategy` 引用必须存在。
9. `conflict.initial <= conflict.peak`。
10. 整个库不允许出现 API Key 形态的字符串。

## 5. 怎么扩展

- **加字段**：只在块内加，且设为可选（不加进 `required`），`schemaVersion` 升 minor。
- **加类目**：现在固定 8 类。真要加第 9 类，必须同时改 `INDEX.json`、`corpus-index.schema.json` 的枚举、校验脚本的类目表——这会是一次 breaking change，走 v2。
- **加难度档**：不建议。前端 `ScenarioDifficulty` 已经是三档，语料再加档会和 UI 打架。
- **不要做的扩展**：把整段提示词塞进 JSON（`promptHints` 只放分寸）、把用户数据塞进语料（语料是静态的，用户数据不进库）。
